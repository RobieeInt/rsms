- Web and API are two parallel route trees over the same domains. `routes/api.php` wraps everything in `Route::name('api.')->group(...)` specifically so API route names (e.g. `api.clients.index`) never collide with the identically-named web ones (`clients.index`) — without the prefix, whichever route file loads last wins the name lookup. Preserve this prefix when adding new API routes.
- Livewire domain folders (`app/Livewire/<Domain>/`) follow a `*List` / `*Form` / `*Show` naming split; `*Form` is shared for both create and edit (route param optional). Follow this pattern for new domains rather than separate Create/Edit components.
- API responses go through `app/Http/Resources/`, one resource per model, mirroring the Livewire domain split — don't return raw models from `Api\*Controller`.
- Authorization is centralized: Policies live in `app/Policies/` and are registered explicitly in `AppServiceProvider::boot()` via `Gate::policy(...)` — NOT relying on Laravel's policy auto-discovery convention. When adding a policy for a new model, register it there or it silently won't apply. Policies alone are NOT enough — every `Api\*Controller` action that reads/writes an owned resource must call `$this->authorize(...)` itself (`app/Http/Controllers/Controller.php` has the `AuthorizesRequests` trait for this). A registered policy that no controller calls is a silent no-op, not a real restriction — this was audited and retrofitted once already (Schedule/Report/Finding/Quotation/Invoice/Client Api controllers), don't let a new controller action skip it.
- `FindingPolicy`/`ReportPolicy` (ownership via `reported_by`/`technician_id` respectively) mirror `SchedulePolicy`'s pattern: admin OR the owning technician for view/update, admin-only for delete.
- Account-management surfaces (creating/editing other users, e.g. `TechnicianList`/`TechnicianForm` on web and `TechnicianController` on API) are gated with the `role:admin` middleware alias (registered in `bootstrap/app.php` — Spatie's `RoleMiddleware`), not left to policy checks alone, since editing another user includes setting their password. Apply this to the whole route group for any future "manage other accounts" feature.
- Public unauthenticated POST endpoints (login, quotation-approval token) carry `throttle:5,1` directly on the route — there's no global API rate limiter configured, so each public write endpoint must throttle itself explicitly or it's brute-forceable.
- Public/unauthenticated-but-secure endpoints (PDF downloads, quotation approval) use Laravel's `signed` URL middleware rather than tokens in the DB, except quotation approval which additionally uses a stored token (`/quotation/approve/{token}`).
- Scheduled billing/reminders are Artisan commands in `app/Console/Commands/`, not queued jobs: `GenerateMonthlyInvoices`, `SendPaymentReminders`, `SendScheduleReminders` — check `routes/console.php` or the scheduler for cadence before assuming when they run. `InvoiceService::generateMonthlyInvoices()` escalates a failed auto-send email to an `AdminAlertNotification` (not just a log line) — follow that pattern for any other auto-generated/auto-sent record.
- Tailwind v4 `@utility` custom utilities only (not `@apply`/`@layer components`). Dark mode toggled via localStorage key `rsms_dark_mode`, not Tailwind's class strategy alone.
- Mobile-first layout in `resources/views/layouts/app.blade.php`: slide-over sidebar (Alpine `sidebarOpen` state on `<body>`), fixed bottom nav (5 tabs) on mobile, hidden on `lg+`.
- Client-facing transactional email is auto-sent on state transitions, never behind a manual "send" button, for Schedule create/update/cancel (`ScheduleCreatedNotification`/`ScheduleUpdatedNotification`/`ScheduleCancelledNotification`, fired from both the Livewire components and the matching `Api\ScheduleController` actions) and for VisitReport completion. A `VisitReport` has NO manual draft/completed toggle in either UI — its `status` is derived purely from its `Schedule`'s status via `App\Services\ReportService::syncStatusWithSchedule()`, called from every place a report can be saved (`Livewire\Reports\ReportForm::saveReport`, `Api\ReportController::store/update`) AND every place a schedule can be checked out (`Livewire\Schedules\ScheduleShow::checkOut`, `Api\ScheduleController::checkOut`) — because either can happen first in practice. The service only flips draft→completed (never the reverse) and only emails the client (`VisitReportSentNotification`) the first time that happens, so it's safe to call redundantly. When adding a new report-save or schedule-checkout code path, call it there too or the auto-complete/auto-email will silently not fire for that path. The still-manual `ReportController::sendEmail` / mobile "Send Email" button remains for ad-hoc resends.
- `TechnicianScheduleNotification` is the one class covering all technician-facing schedule emails, distinguished by its `$type` (`created|reminder|reassigned|cancelled`) rather than separate classes per event — when a schedule's `technician_id` changes on an existing schedule (in `ScheduleForm::save()` or `Api\ScheduleController::update`), both the outgoing technician (`type: cancelled`) and incoming technician (`type: reassigned`) must be notified; this wasn't happening before and is easy to forget when adding a new place schedules get reassigned.
- `QuotationForm::mount()` accepts an optional `?finding=<id>` query string (not a route param) from the "Create Quotation" button on `finding-show.blade.php`, prefilling client + one line item from `QuotationService::createFromFindings()`'s item shape — it does NOT auto-submit, the admin still reviews/prices before saving. Keep this working if `QuotationForm` or the finding-show link is refactored.
- **Internal-only fields on client-facing records** (e.g. `QuotationItem`/`InvoiceItem.cost_price`, `Client.retainer_cost` — cost/"modal" documentation, admin-only, never shown to the client or technicians): a Livewire component's public properties are serialized into the page's HTML (`wire:snapshot`) regardless of whether the blade renders an input for them, so **hiding the blade input with `@if(hasRole('admin'))` is not enough** — the value must never be loaded into the public property in the first place for a non-admin (gate it in `mount()`), or it leaks via page source. Symmetrically, on `save()`, don't blanket-null the field for non-admins (that silently destroys existing admin-entered data on any unrelated edit) — restore it from a fresh DB read instead, since these forms recreate all line items on every save (delete + re-`create()`, no per-item identity) rather than diffing. This full pattern (`QuotationForm`/`InvoiceForm`/`ClientForm`) is the template to copy for any future admin-only/internal field.
